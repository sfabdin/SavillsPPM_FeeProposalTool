1 What it is

A multi-page internal app that builds, prices, stores, and reports on client fee proposals. A user assembles a project team (roles × tiers × allocation), the app prices it against a confidential rate grid with escalation, rate-lock and discount logic, and produces a formula-driven Excel proposal. Projects are saved to a shared database in Box, which feeds a projects index, a revenue-projection view, and downstream reporting (Power BI / Clockify).

It is not a framework app — there is no build step, no npm install to run it, no React. It is plain HTML, CSS and vanilla JavaScript served as static files, plus two small serverless functions. A developer can open any file and read it directly. That simplicity is deliberate and worth preserving.

4 How the data works

Every project is one JSON record holding inputs only — roles, tiers, allocation %, assumptions, dates, Salesforce ID. Dollar figures are never stored; they are recomputed live from the inputs each time a page renders. (This is why a calculation fix instantly corrects every existing project — there is nothing stale to migrate.)

All records live in a single file, projects.json, in a Box folder. The app keeps two mirrored copies:

  • localStorage (in the browser) — the fast working copy; every edit writes here instantly.
  • Box — the shared source of truth. On load the app pulls Box → local; after edits it debounce-pushes local → Box. Concurrent saves are merged newest-edit-wins per project, guarded by an etag.

The Salesforce ID on each booked record is the join key that links projects.json → Salesforce → Clockify for downstream reporting. Reporting tools read projects.json from Box directly — they do not go through the app.

5 The confidential rate grid

The single most important rule The rate numbers must NEVER be committed to the repo. Anything in the deployed bundle is readable at its URL with no login. The grid lives only in Box as rates.json.

rates-catalog.js (in the repo) is the engine — the High/Mid/Low math and title→family mapping, no numbers. On boot the app pulls rates.json from Box and hydrates the engine in memory. If the file is missing or its id is unset, every page shows a "Rate card unavailable" gate rather than running with blank rates. .gitignore blocks rates.json from being committed; .vercelignore blocks it (and research/) from deploying.

6 Access & permissions

Sign-in is Box OAuth — no Box login, no app. Once in, visibility is fail-closed:

  • Admins (allowlist in store.js) see every project.
  • Everyone else sees only the projects they lead or own.
  • An unrecognized login sees nothing until explicitly added.

To grant or revoke all-access, edit the ADMINS set at the top of store.js. A single super-user (set by SUPERUSER) gets a hidden "Viewing as" switch on the Projects Index to preview anyone's restricted view — no one else can.

Honest limit The per-person wall is enforced in the browser, and the Box folder permission is the real boundary: anyone with folder access can read projects.json directly. Fine for a trusted leadership group. Restricting a person who should see some but not all projects requires server-side filtering — a future build, not yet present.

7 The Excel export

Generated client-side (ExcelJS) with live formulas, not pasted values — open any cell to read the math. Four tabs:

  1. Setup & Summary — project info, assumptions, rates table, headline totals.
  2. Phase Matrix — FTE allocation by period with phase-fee formulas.
  3. Monthly Detail — two stacked sections: editable allocation % on top driving fee $ below.
  4. Billing Summary — invoiced net by group, by month (discount + rate-lock baked in), with a reconciliation bridge.

8 The calculation pipeline

Every dollar the app shows is derived live from inputs through the exact sequence below. The same math is implemented twice — in app.js (the calculator) and store.js (the index, projections and benchmarking). Both must agree; they were reconciled and verified to the dollar.

Step 1 · Timeline → months

The start and end month/year are enumerated inclusively into a list of calendar months. Every month in range counts as a whole month — there is no day-level proration.

Step 2 · Months → phases

Each phase has a length in months; months are assigned to phases in order. Phases auto-rebalance so their lengths sum to the total month count, with any remainder going to the last phase.

Step 3 · Allocation per role-month

For each role in each month, the effective FTE % is the per-month override if one exists, otherwise the phase-level FTE %. (Editing one month pins its siblings; the phase value becomes a display average.)

Step 4 · Base rate & anchor year

Role typeBase rateAnchor year
Gridrack rate × (1 − industry adj %)catalog base year (2024)
Contractedthe entered rate, as-is (industry adj bypassed)project start year
No-charge$0 (PIC / advisory)—

Step 5 · Escalation

rate(year) = base × (1 + escalation%) ^ (calendarYear − anchorYear)
Compounds annually, stepping on January 1 of each calendar year.

Step 6 · Published monthly fee

monthlyFee = effectiveFTE% × rate(month's year) × hoursPerMonth
Always at the unlocked (full escalated) rate. hoursPerMonth = 173.33 (2080 / 12).

Step 7 · Roll-ups & the gross → net waterfall

LineFormula
Gross feeΣ published monthly fee, all roles × all months
− Rate Lock creditΣ max(0, unlockedRate − lockedRate) × FTE × hrs  (lockedRate is pinned to the start year)
− Client discountGross × discount %
= Net (proposed fee)Gross − Rate Lock credit − discount — what the client pays
− Fee shareNet × fee-share %  (broker cut, revenue side, invisible to client)
= RevenueNet − fee share — what Savills keeps
The rate-lock rule (this was a real bug, now fixed) Gross is computed at the full published rate. Rate Lock appears once, as the credit line. The earlier code baked the locked rate into gross and subtracted the credit — double-removing it. Net now equals exactly what the client pays at locked rates.

Step 8 · Cost-floor check (advisory only — does not change the fee)

Each grid role's lowest billed rate — rate(startYear) × (1 − discount%) — is compared to the tier's confidential cost floor. If it falls below, the role is flagged "below cost." This is a warning only; it never alters the calculated fee.

9 Calculation caveats & exceptions

The math is deterministic, but several behaviors are easy to misread. Each is listed with how it behaves today and how it's accounted for.

CaveatBehavior & how it's handled
Escalation steps on Jan 1 Escalation is keyed to the calendar year, not the engagement anniversary. A project starting Dec 2027 jumps a tier after one month (Jan 2028). Intended (aligns to fiscal rate cards) — but flag it to anyone pricing a December/Q4 start.
Discount is on gross The client discount is computed on the published gross, not on the post-Rate-Lock figure. Deliberate, so every waterfall line ties to the one above it. Net effect: marginally larger discount than discount-on-net would give (difference = discount% × lock credit).
Rate Lock can be a no-op A credit only arises when escalation > 0 and the project runs past its start year. Single-year or 0%-escalation projects: Rate Lock changes nothing (credit = $0). Not a bug — there is simply nothing to lock.
Contracted roles Bypass the industry adjustment and anchor at the start year (the typed rate = exactly what's billed in year 1). They still escalate forward unless locked, and are still checked against the selected tier's grid cost floor — so pick a sensible tier even for a contracted rate.
Display rounding Every figure shown is rounded to whole dollars while the math runs at full precision — so a column of rounded rows can read $1–2 off the rounded total. Cosmetic only. The Excel export uses full-precision formulas and does not drift.
No-charge tiers PIC / advisory no-charge tiers price at $0 and are exempt from the cost-floor check. Expected.
Per-month overrides Editing one month pins its siblings to their current values (so they don't drift toward an average); the phase cell becomes a display-only average. Typing into the phase cell re-broadcasts evenly to all its months.
Flatline billing Bills net ÷ months evenly, discarding the staffing curve. In flatline, a group's share of each month is proportional to that group's gross. Resource-loaded mode tracks the real curve.
Whole-month basis 173.33 hrs = one full month at 100% FTE. Months aren't pro-rated by day, so a mid-month start/finish still counts as a full month scaled by FTE %. Trim the FTE % to approximate a partial month.
Two engines must stay in sync The calculator (app.js) and the index/projections (store.js) reimplement the same math. A change in one must be mirrored in the other — the rate-lock fix had to be made in both. Verified equal to the dollar after each change.

Fixed while documenting this

Tier fallback aligned A role with an unrecognized/legacy tier id fell back to Mid in the calculator but to High in the projections engine — which could price a malformed role higher in Projections than in the calculator. Both now fall back to Mid. Edge case (only malformed/legacy ids), now consistent.

Recommended follow-ups

  • Escalation basis note — surface "escalates on Jan 1" in the UI, or offer anniversary-based escalation as an option, so Q4-start pricing isn't a surprise.
  • Parity self-check — a dev-mode assert that app.js net equals store.js net for the open project, to catch the two engines drifting before anyone notices in production.
  • "Discount on gross" footnote — one line in the summary so the basis is explicit to reviewers.

10 Reconcile-to-target & staffing mock-up

When a record carries a proposal total (typed, or extracted by Ingestion), the Reconcile to proposal bar back-solves to it. There are two paths, chosen automatically by whether the staffing matrix is already populated.

Path A · staffing exists → solve the discount

If roles are allocated (gross > 0), Fit to target holds staffing and rates fixed and solves the client discount to hit the target. The discount is stored at full precision (e.g. 13.306045%), so net reconciles to the penny — the panel confirms "reconciled to the penny" only when truly exact. If the target is above what current rates can bill at 0% discount, it reports the shortfall and leaves rates for a manual change.

Path B · no hours stated → mock up logical staffing

If the proposal named people but stated no hours (blank matrix), Fit to target builds a logical staffing shape instead:

  • Only named people are staffed — never invents bodies.
  • Every person gets some allocation, shaped by seniority: delivery roles (PM / Sr PM) carry the load, principals / EVPs are light-touch oversight, coordinators in between.
  • That shape is scaled to bridge to the fee, water-filled with 100% caps so no one exceeds full time.
  • If the target exceeds the team's capacity, everyone maxes at 100% and the shortfall is reported — nothing is invented past 100%.
  • If nothing can be priced (no rates), allocations are left blank and the reason is shown — no fabrication.

The two paths chain: mock up the staffing, then Fit to target again to lock the penny via a micro-discount. The seniority weights are the only assumed numbers in the whole system, and apply only when the proposal states no hours.

11 Reporting & derived figures

Records store inputs; the pipeline derives the dollars live. For reporting (Power BI), the rule is: snapshot the answers at booking, recompute everything else live.

Design principle Snapshot the results, never the recipe. The math lives in one place (the app). Do not reimplement the pipeline in DAX / report formulas — that would be a third engine to keep in sync and would drift.

Booked figures are frozen facts

A booked fee is contractual — it must not silently change because the rate card, a bug fix, or an assumption changed later. On the Won / Active transition (the same trigger as the Salesforce intake), the record should carry a financials snapshot:

"financials": { "computedAt": "2026-06-09T14:22:31Z", when frozen "engineVersion": "2026.06", which pipeline produced it "basis": "booked", "gross": 1886139.00, "rateLockCredit": 27874.00, "discount": 188614.00, "net": 1669651.00, the proposed fee (what the client pays) "feeShare": 0, "revenue": 1669651.00, net of broker fee share "byMonth": [ { "ym": "2027-01", "net": 64210.00 }, ... ], "byGroup": [ { "group": "Core team", "net": 980400.00 }, ... ] }

Power BI reads this block directly — no recomputation, no formula logic on the reporting side. The engineVersion + computedAt stamps let reporting distinguish old snapshots from new if the pipeline ever changes.

Pre-booking projects stay live

Draft / negotiation records have no snapshot — their numbers are working estimates and should recompute live in the app's projection views. Reporting either ignores them or reads them clearly labelled as "live estimate," never as committed revenue.

Keeping a snapshot honest

A snapshot can drift if someone edits a booked project afterward. The existing intake drift detector already catches this: editing a booked project re-flags the intake and should re-stamp the financials snapshot (or be processed as a change order). That freezes the booked number without ever letting it silently mutate.

Status · implemented The financials snapshot is live in store.js. It freezes on the first booked save (won / active / closed) via saveProject, agrees with the live engine to the penny, and byGroup / byMonth tie to net. Editing a booked record's inputs sets financials.stale = true without overwriting the frozen numbers; restampFinancials(id) refreshes them on an approved change order. Pre-booking records carry no snapshot.

13 Deploying a change

Source of truth is the GitHub repo; Vercel auto-deploys on push.

  1. Edit the file(s) in the repo.
  2. Commit & push to the main branch.
  3. Vercel builds and deploys automatically (static — no build step, seconds).
  4. Hard-refresh the live site to confirm.
Box app setup (one-time) Box Developer Console → your app: Auth method = User Authentication (OAuth 2.0); enable Authorization Code Grant with PKCE; Redirect URI = https://<your-vercel-domain>/oauth-callback.html; scope = Read/write all files. Each deploy origin (preview + prod) needs its own registered redirect URI.

14 Known operational caveats

  • Client-side access limit (see §6) — Box folder permission is the true boundary.
  • rates.json must exist in Box with its id set, or the app gates closed.
  • Box logins must match the allowlist emails exactly (firstinitiallastname@savills.us). A mismatch makes an admin look like a member.
  • Intake drift flags after a calc fix — correcting the math changes booked figures slightly, so lock-on booked projects may read "re-submit intake." Expected, not a bug.
  • Two copies of the code — keep ONE source of truth. If edits are ever made both here and elsewhere, they diverge.
  • Token refresh — sign-in survives ~60 days idle; after that the user re-authenticates. Normal.
