Fee & Revenue System

How this application is built, where its data lives, how to deploy it, and what to watch out for. Written for a future owner or developer inheriting the tool. Every statement here describes what the system does today, not what it might do.
Status  Live, in production use Stack  Static HTML/JS + Vercel functions + Box Updated  July 2026

1 What it is

A multi-page internal app that builds, prices, stores, and reports on client fee proposals. A user assembles a project team (roles × tiers × monthly allocation), the app prices it against a confidential rate grid with escalation, rate-lock and discount logic, produces a formula-driven Excel proposal, and saves the project to a shared database. That database feeds a projects index, revenue projections, Revenue Reconciliation (the monthly close), proposal analytics, benchmarking, change orders, and downstream reporting (Power BI / Clockify).

It is not a framework app — no build step, no npm install to run it, no React. It is plain HTML, CSS and vanilla JavaScript served as static files, plus two small serverless functions. A developer can open any file and read it directly. That simplicity is deliberate and worth preserving.

The one-sentence mental model The website deployed on Vercel is an empty shell — a door. It contains no fees, no rates, no client data. When a user signs in with Box (OAuth), the door opens and the app pulls the real data out of Box into the browser for that session. Everything confidential lives in Box and only in Box.

4 How the data works

Every project is one JSON record. Records carry two kinds of value, and the distinction is the most important thing to understand about the data model:

  • Inputs — roles, tiers, monthly allocation %, assumptions, dates, Salesforce ID. On every project. The dollar figures shown on screen are recomputed live from these inputs each time a page renders, so a calculation fix instantly corrects every project with no migration.
  • A frozen financials snapshot — real dollar figures (gross, rate-lock credit, discount, net, revenue, plus a billingSeries with net / broker / invoice per month and by-group arrays). This is written onto a record when it is booked (won / active / closed), and it does not recompute — it is a contractual fact frozen at booking. Pursuits (draft / negotiation) also carry a billing series, but theirs is live-refreshed on every save, never frozen — it exists so Projections read one stored series everywhere instead of recomputing. NTE-basis projects auto-restamp on edit (an NTE plan is an estimate, not a frozen contract). See §11–12.

Beyond the record itself, the data layer keeps: version history (manual + auto versions per project, with diff and restore), soft-delete tombstones (deletes propagate through the multi-user merge instead of resurrecting; purged after 120 days), an append-only activity log (create / status change / book / delete, with actor and timestamp, union-merged across users), and a schema-migration runner — projects.json carries a schema version and old records upgrade automatically on load.

Yes, there are dollar numbers in projects.json now Booked records contain hard dollar figures in their financials block — this is intentional and is what downstream reporting reads. Those numbers live in projects.json inside Box. They are never in the deployed app, never in GitHub. The app on Vercel ships with zero fees and zero rates; it only ever fetches them from Box after the user authenticates.

All records live in a single file, projects.json, in a Box folder. The app keeps two mirrored copies:

  • localStorage (in the browser) — the fast working copy; every edit writes here instantly.
  • Box — the shared source of truth. On load the app pulls Box → local; after edits it debounce-pushes local → Box, and flushes any pending push the moment the tab hides or closes. Concurrent saves merge newest-edit-wins per project (tombstones win over stale copies; activity logs union), guarded by an etag. On sign-out the local copy is cleared so no data lingers on a shared machine.

The Salesforce ID on each booked record is the join key that links projects.json → Salesforce → Clockify. Reporting tools read projects.json from Box directly — they never go through the app.

5 The confidential rate grid

The single most important rule The rate numbers must NEVER be committed to the repo. Anything in the deployed bundle is readable at its URL with no login. The grid lives only in Box as rates.json.

rates-catalog.js (in the repo) is the engine — the High/Mid/Low math and title→family mapping, with no numbers in it. On boot, after the user authenticates, the app pulls rates.json from Box and hydrates the engine in memory for that session. If the file is missing or its id is unset, every page shows a "Rate card unavailable" gate rather than running with blank rates. .gitignore blocks rates.json from being committed; .vercelignore blocks it (and research/) from deploying.

6 Access & permissions

Sign-in is Box OAuth — no Box login, no app. The deployed page is a shell until a valid Box token loads the data. Once in, visibility is fail-closed:

  • Admins (ADMINS in store.js, plus any email in the synced vocabulary's admins list) get the admin tools and see every project.
  • Tool admins (TOOL_ADMINS, plus the vocabulary's toolAdmins list) get the admin tools but keep member project access — they still see only what they lead / own / are granted. For people who run an operational function without needing the whole firm's fee book.
  • Granting admin without a deploy: a superuser runs UFC_Store.addVocab({ admins: ['name@savills.us'] }) (or toolAdmins: […]) in the browser console on any page. The grant is stored in the shared database, syncs to Box like any other edit, and takes effect for that person on their next page load. The hardcoded sets in store.js remain the bootstrap floor — removals still require a deploy, which is deliberate (fail-closed).
  • Everyone else sees only the projects they lead or own.
  • An unrecognized login sees nothing until explicitly added.

Two functions, two jobs — mixing them up is the easy way to leak data:

  • isAdmin(user) → may they open this TOOL? True for admins and tool admins. Use it for page gates and nav links.
  • seesAllProjects(user) → may they see EVERY project's data? True for ADMINS only. Every data-visibility decision must use this — visibleProjects, the calculator's access wall, Change Log scope, Proposal Analytics.

To grant or revoke access, edit ADMINS / TOOL_ADMINS near the identity block in store.js. Per-user extra visibility (e.g. every project carrying a "Change Management" group) lives in GROUP_ACCESS. Super-users (SUPERUSERS) get a hidden "Viewing as" switch to preview anyone's restricted view — no one else can.

The security model, stated plainly Box folder membership is the boundary. Everything above is scoping, enforced in the browser from an email list compiled into public JavaScript. Anyone who is a collaborator on the shared Box folder can read every file in it directly, and can make themselves "admin" from the browser console. That is acceptable for a trusted team on one Box folder and it is not fixable without a server in front of the data — so it is written down here rather than pretended otherwise. What is enforced server-side: the two serverless functions (/api/clockify, /api/extract) accept only a Box token that belongs to a Savills login and can see the shared folder, and /api/extract is rate-limited per person. Sign-in uses PKCE and a checked state nonce; the token bundle (including the refresh token) is kept in localStorage by decision, with a Content-Security-Policy on every response as the main defence against script injection. Nothing third-party is loaded at runtime; the Excel and PDF libraries are vendored under /vendor.

8 The calculation pipeline

Every dollar the app shows is derived live from inputs through the exact sequence below. The same math is implemented twice — in app.js (the calculator) and store.js (the index, projections and benchmarking). Both are month-canonical and were reconciled and verified equal to the dollar.

Step 1 · Timeline → months

The start and end month/year are enumerated inclusively into a list of calendar months. Every month in range counts as a whole month — there is no day-level proration.

Step 2 · Months are the source of truth; phase is a rollup

Allocation is stored per month. A phase is a calculated convenience: the phase % shown is the average of its months, and editing a phase cell is a shortcut that broadcasts that value to every month in the phase. All dollars are computed from the months, never from the phase. Phases auto-rebalance so their lengths sum to the month count.

Step 3 · Effective allocation per role-month

For each role in each month, the effective FTE % is that month's stored value (a per-month edit), falling back to the phase value if a month was never individually set.

Step 4 · Base rate & anchor year

Role typeBase rateAnchor year
Gridrack rate × (1 − industry adj %)catalog base year (2024)
Contractedthe entered rate, as-is (industry adj bypassed)project start year
No-charge$0 (PIC / advisory)—

Step 5 · Escalation

rate(year) = base × (1 + escalation%) ^ (calendarYear − anchorYear)
Compounds annually, stepping on January 1 of each calendar year.

Step 6 · Monthly fee

monthlyFee = effectiveFTE% × rate(month's year) × hoursPerMonth
Always at the unlocked (full escalated) rate. hoursPerMonth = 173.33 (2080 / 12).

Step 7 · Roll-ups & the gross → net waterfall

The rate-lock rule Gross is computed at the full published rate. Rate Lock appears once, as the credit line. (An earlier version baked the locked rate into gross and subtracted the credit, double-removing it — fixed in both engines. Net now equals exactly what the client pays at locked rates.)

Step 8 · Cost-floor check (advisory only — does not change the fee)

Each grid role's lowest billed rate — rate(startYear) × (1 − discount%) — is compared to the tier's confidential cost floor. If it falls below, the role is flagged "below cost." A warning only; it never alters the calculated fee.

9 Calculation caveats & exceptions

The math is deterministic, but several behaviors are easy to misread. Each is listed with how it behaves today and how it's accounted for.

CaveatBehavior & how it's handled
Escalation steps on Jan 1 Escalation is keyed to the calendar year, not the engagement anniversary. A project starting Dec 2027 jumps a tier after one month (Jan 2028). Intended (aligns to fiscal rate cards) — but flag it to anyone pricing a December/Q4 start.
Discount is on gross The client discount is computed on the published gross, not on the post-Rate-Lock figure. Deliberate, so every waterfall line ties to the one above it. Net effect: marginally larger discount than discount-on-net would give (difference = discount% × lock credit).
Rate Lock can be a no-op A credit only arises when escalation > 0 and the project runs past its start year. Single-year or 0%-escalation projects: Rate Lock changes nothing (credit = $0). Not a bug — there is simply nothing to lock.
Contracted roles Bypass the industry adjustment and anchor at the start year (the typed rate = exactly what's billed in year 1). They still escalate forward unless locked, and are still checked against the selected tier's grid cost floor — so pick a sensible tier even for a contracted rate.
Display rounding Every figure shown is rounded to whole dollars while the math runs at full precision — so a column of rounded rows can read $1–2 off the rounded total. Cosmetic only. The Excel export uses full-precision formulas and does not drift.
No-charge tiers PIC / advisory no-charge tiers price at $0 and are exempt from the cost-floor check. Expected.
Phase edits broadcast Editing a phase cell overwrites every month in that phase with the typed value (the shortcut). Editing a single month changes only that month; the phase then displays the new month average. Months are always the stored truth.
Flatline billing Bills net ÷ months evenly, discarding the staffing curve. In flatline, a group's share of each month is proportional to that group's gross. Resource-loaded mode tracks the real curve.
Whole-month basis 173.33 hrs = one full month at 100% FTE. Months aren't pro-rated by day, so a mid-month start/finish still counts as a full month scaled by FTE %. Trim the FTE % to approximate a partial month.
Two engines must stay in sync The calculator (app.js) and the index/projections (store.js) reimplement the same math. A change in one must be mirrored in the other. Verified equal to the dollar after each change.

Recommended follow-ups

  • Escalation basis note — surface "escalates on Jan 1" in the UI, or offer anniversary-based escalation as an option, so Q4-start pricing isn't a surprise.
  • Parity self-check — a dev-mode assert that app.js net equals store.js net for the open project, to catch the two engines drifting before anyone notices in production.
  • "Discount on gross" footnote — one line in the summary so the basis is explicit to reviewers.

10 Reconcile-to-target & staffing mock-up

When a record carries a proposal total (typed, or extracted by Ingestion), the Reconcile to proposal bar back-solves to it. Two paths, chosen automatically by whether the staffing matrix is already populated.

Path A · staffing exists → solve the discount

If roles are allocated (gross > 0), Fit to target holds staffing and rates fixed and solves the client discount to hit the target. The discount is stored at full precision (e.g. 13.306045%), so net reconciles to the penny — the panel confirms "reconciled to the penny" only when truly exact. If the target exceeds what current rates can bill at 0% discount, it reports the shortfall.

Path B · no hours stated → mock up logical staffing

If the proposal named people but stated no hours (blank matrix), Fit to target builds a logical staffing shape: only named people are staffed; everyone gets some allocation shaped by seniority (delivery roles carry the load, principals light-touch); the shape is scaled with 100% caps to bridge to the fee. If the target exceeds the team's capacity it maxes at 100% and reports the shortfall; if nothing can be priced it leaves allocations blank. The seniority weights are the only assumed numbers in the system, used only when no hours are stated.

11 Change orders

A change order (CO) amends a booked contract. The model: original contract + Σ approved change orders = revised contract.

  • Forked, linked record. "Process as change order" on a booked project creates a new record — a full, month-canonical copy of the running revised scope — named {Project} — CHANGE ORDER n (Mon YYYY), sharing the parent's Salesforce ID (no new SF project).
  • Incremental scope. A CO's value is the difference between its priced net and the contract it forked from. The baseline curve is never reset; the delta naturally starts where the months diverge. COs can be negative (de-scope).
  • Differences-only panel. While editing a CO, the banner shows a live role-level diff — roles added / removed / changed (FTE-months and rate) — plus the incremental dollar value and effective month.
  • Approval freezes it. Approving a CO snapshots its financials and sets it active, so it rolls into the revised contract. Only approved COs roll in.
  • Rolls up everywhere. The Projects Index shows the revised contract per project and a by-client rollup; Revenue Projections folds each approved CO's incremental into the parent's monthly curve. COs are never separate line items in either rollup.
Stale-contract flag If a booked project's inputs drift from its frozen snapshot, the calculator shows a red banner — "Contract changed since it was booked" — with two actions: Restamp contract (restampFinancials refreshes the frozen figures to current scope) or Process as change order (capture the difference as a signed amendment).

12 Reporting & the financials snapshot

Records store inputs that recompute live; booked records also carry frozen dollar figures for reporting. The rule: snapshot the answers at booking, recompute everything else live.

Design principle Snapshot the results, never the recipe. The math lives in one place (the app). The reporting side reads the frozen numbers and does not reimplement the pipeline in DAX / report formulas — a third engine would only drift.

What gets frozen, and when

On the first booked save (won / active / closed), saveProject writes a financials block onto the record. It is real dollar figures, stamped with the engine version and timestamp, and it does not recompute:

"financials": { "computedAt": "2026-06-09T14:22:31Z", when frozen "engineVersion": "2026.06", which pipeline produced it "basis": "booked", "gross": 1886139.00, "rateLockCredit": 27874.00, "discount": 188614.00, "net": 1669651.00, the proposed fee (what the client pays) "feeShare": 0, "revenue": 1669651.00, net of broker fee share "byMonth": [ { "ym": "2027-01", "net": 64210.00, "broker": 6421.00, "invoice": 64210.00 }, ... ], "byGroup": [ { "group": "Core team", "net": 980400.00 }, ... ], "feeBasis": "fixed", "fixed" or "nte" (NTE auto-restamps) "stale": false true if inputs drifted since }

This block lives in projects.json in Box. Power BI reads it directly via the Box file — no app, no recomputation. byGroup and byMonth tie to net; the snapshot agrees with the live engine to the penny at the moment it is taken.

Pre-booking projects stay live

Draft / negotiation records have no snapshot — their numbers are working estimates and recompute live in the projection views. Reporting either ignores them or treats them clearly as "live estimate," never as committed revenue.

Keeping a snapshot honest

A snapshot would drift if someone edits a booked project afterward. The app does not silently overwrite it: editing a booked record sets financials.stale = true and the calculator shows the stale-contract banner (§11). The figures only refresh on an explicit restamp or are superseded by an approved change order. A booked number never changes by accident.

Status · implemented The snapshot, stale flag, restamp, and change-order roll-up are all live in store.js and the calculator UI, and verified end-to-end.

The audit trail (activity log)

An append-only activity array rides inside projects.json, so the history syncs with the data and is union-merged by entry id in mergeDb — two people editing offline both keep their entries. Capped at the most recent 1,500; oldest fall off the front.

Every entry carries ts, actor (real Box login — never the impersonated one), actorName, action, projectId and a meta payload. Actions: create, edit, status, book, delete. When an admin acts while using "View as", the entry also records viewingAs — accountability follows the real identity.

describeChanges(prev, next) in store.js produces the field-level diff on every save: project meta, revenue leader, rating, timeline, phases, groups, all assumptions, broker fee share, pass-through lines, and the roster (through the same rosterDiff that powers version history). feeDelta() adds net-fee before/after when the rate grid is loaded. Logging is wrapped in try/catch at every level — a logging failure must never break a save.

Note · log vs. versions The change log answers "who touched this and what did they move?" Version history answers "put it back the way it was." They are separate systems by design — the log is cheap and global, versions are heavy per-project snapshots.

The actuals layer (Clockify → staff.json)

Actual hours never touch projects.json. They live in staff.json alongside the staffing matrix, notes and the mapping tables. api/clockify.js is a serverless proxy over Clockify's Reports API — it aggregates server-side and returns a small CSV of hours by user × project × month, so the browser never pages raw time entries and the API key never leaves the server. It also serves project and user lists, plus an entry-lateness report (creation time decoded from each entry's ObjectID vs. the day worked).

Two mapping tables make it usable, both saved to staff.json so a fix by one admin holds for everyone: fee-link (Clockify project → fee record) and title pinning (person → grid title, for cost rate). Unmapped Clockify projects surface as unattributed burn on the Profitability page rather than being silently dropped. Cost rates come from rates.json — so burn, like every other number, reconciles to the same grid.

14 Deploying a change

Source of truth is the GitHub repo; Vercel auto-deploys on push.

  1. Edit the file(s) in the repo.
  2. Commit & push to the main branch.
  3. CI runs on every push (.github/workflows/tests.yml): HTML hygiene on every page, the regression suite (tests.html — engine, data layer, staffing, exec model, round trips, a Box fake for the 412 merge path), the Executive Reporting invariants, the client-workbook wiring check, and a Chromium smoke of every page. All five must be green before a merge. Locally: node scripts/check-html.mjs && node scripts/run-tests.mjs && node exec-reporting/verify-core.mjs && node scripts/check-export.mjs && node scripts/smoke.mjs.
  4. Vercel builds and deploys automatically (static — no build step, seconds).
  5. Hard-refresh the live site to confirm.
What the browser caches (vercel.json) Pages, scripts, stylesheets and JSON are always revalidated (max-age=0, must-revalidate): the browser asks once per file and gets a 304 when nothing changed, so a deploy shows up on the next navigation and a page can never run against a stale script. (A ten-minute script cache was tried and produced exactly that skew — an old calculator against a new store — so it was removed.) Fonts, icons and logos are cached for a week; /vendor/ for a day. There are no ?v= stamps to bump: don't add any.
Script order on a page Every page loads, in this order: vendor-lazy.js (only if it exports) → rates-catalog.js → store.js → box-adapter.js → boot.js → ui.js → sync-status.js → staff.js (only if it reads staffing) → the page's own controller → guide.js → nav.js. Before boot.js, set window.UFC_NEEDS to the extra Box stores the page reads ('staff', 'studio', 'revenue', 'activity'); projects and rates always load. Page-specific CSS lives in universal-fee-calc/<page>.css, not in a <style> block, so it can be cached.
One vocabulary Shared helpers live in ui.js (UFC_UI.esc, MONTHS, ymLabel / monthLabel, fmtMoney, debounce, toast) — a page controller aliases them, it never carries its own copy. Months display as mmm-YY (Sep-26) everywhere. Named once in the store and used by name: BOOKED_STATUSES / CO_ELIGIBLE_STATUSES / ENDED_STATUSES, PRICING_HOURS_PER_MONTH (173.33, what a fee is priced on) and CAPACITY_HOURS_PER_MONTH (172, what a person can log), defaultAssumptions() for the record shape, and tokenScore() — the one name matcher behind staffing, revenue import and reconciliation. Storage keys keep their existing shapes: the projects book keys months as YYYY-M (monthlyOverrides, fteMonthly), the staffing book as YYYY-MM. Only the display format was unified.
Box app setup (one-time) Box Developer Console → your app: Auth method = User Authentication (OAuth 2.0); enable Authorization Code Grant with PKCE; Redirect URI = https://<your-vercel-domain>/oauth-callback.html; scope = Read/write all files. Each deploy origin (preview + prod) needs its own registered redirect URI.
The Box copy of the code is storage, not the runtime A copy of the app files may sit in the Box folder for safekeeping (e.g. a "DO NOT OPEN" folder). It is not what users run — Box serves HTML as a download, can't run the serverless functions, and can't complete OAuth. Users always open the Vercel URL. Keep GitHub as the single source of truth.

15 Known operational caveats

  • Client-side access limit (§6) — Box folder permission is the true boundary.
  • rates.json must exist in Box with its id set, or every page gates closed.
  • Box logins must match the allowlist emails exactly (firstinitiallastname@savills.us). A mismatch makes an admin look like a member.
  • Editing a booked project flags it stale — by design (§11). Restamp or process a change order. NTE projects restamp automatically.
  • Run tests.html before every deploy — 24 regression assertions on the pricing engine and data layer; all must be green.
  • Clockify mapping hygiene — an unmapped Clockify project shows as unattributed burn on Profitability. Fix the fee-link once and it holds for the whole team (§12).
  • Staffing data looks wrong (duplicates, 200%+ loads, ghost rows)? Open Data Repair first — it previews every known damage signature before touching anything, and its deletions use tombstones so a stale tab can't merge them back. Anything it lists under "needs human review" is a judgment call it will not auto-fix.
  • Project renamed? Use the canonical-sync rename flow (Mapping tab) rather than editing rows by hand — the saved rename table is what keeps the contract↔staffing bridge, coverage checks and future imports pointing at one name.
  • Token refresh — sign-in survives ~60 days idle; after that the user re-authenticates. Normal.
  • Claude model changes can't break Ingestion — api/extract.js tries a built-in list of model ids in order and uses the first that responds; a deprecated model is skipped automatically.
