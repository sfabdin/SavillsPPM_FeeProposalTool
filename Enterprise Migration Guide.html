Part 2

Where the data lives — three backends.

The app and its reporting stay exactly as they are in every option. The only code that changes is the storage layer — store.js, the one file that today reads and writes the browser. Point it somewhere shared and the whole team works off one set of projects. Here's how the realistic choices compare for PPM.

Box + Vercel

Best fit
Data stays in Savills' existing Box tenant; app hosted on Vercel.
How it works
  • The whole database is already one JSON file (that's what Export DB produces). It lives as projects.json in a shared Box folder.
  • store.js pulls it from Box on load, writes it back on save — via the Box API.
  • Reporting (Projections, etc.) stays right here in the app.
Why it wins for you
  • Governance already sorted — client fee data never leaves your tenant.
  • No new SaaS subscription or IT onboarding.
The one guardrail
  • It's a whole-file store, so simultaneous saves can clobber. Needs a light save protocol (pull-merge-write with a timestamp/lock check) — small addition, removes the only real risk. Fine for a small team of occasional editors.

Airtable + Vercel

A true shared database; app hosted on Vercel.
How it works
  • The four tables (Projects, Roles, Phases, Rates) live as Airtable records.
  • store.js calls the Airtable API — row-level, so no clobbering.
  • Non-technical folks can browse/edit records in Airtable's grid directly.
Cost
  • A SaaS subscription, and it lives outside Savills' Microsoft/Box estate — worth a governance check for client data.

SharePoint + Fabric

Native M365; heaviest but most powerful.
How it works
  • Four SharePoint Lists (Part 1) as the database; store.js calls Graph/REST.
  • Power BI / Fabric does enterprise reporting + Clockify P&L (Part 3).
Cost
  • Most build effort; rate math has to be re-expressed in DAX for Power BI (Part 4).
  • Worth it only if you want firm-wide BI + automation, not just a shared app.
Common thread: all three are the same store.js swap — the calculator, ingestion, reconcile, floor checks, and Revenue Projections are untouched in every case. You're only choosing where the records live. Box + Vercel is the lightest path that keeps data in your tenant; the SharePoint/Fabric detail below is there if you later want native BI.

About Vercel (the hosting piece). Vercel just puts these HTML files online at a URL the team opens — it replaces "double-click the file." It is not a database, which is why it pairs with Box or Airtable for shared data. Lowest-effort hosting there is; could be live the same day. (You could also host on Box's own web hosting or an internal server — Vercel is just the easy default.)

Part 2b

If you go SharePoint — app options.

Only relevant if you choose the Microsoft route. Two ways to run the authoring screens on it.

Keep the HTML app

Recommended
Host as-is; swap only the storage layer to SharePoint.
Why
  • Rate engine, floor checks, reconcile, projections — all carry over untouched.
  • Only store.js changes (localStorage → Graph/REST calls).
  • Fastest route to multi-user; weeks not months.
Cost
  • Hosted as a SharePoint page, SPFx web part, or Azure Static Web App.

Rebuild in Power Apps

Canvas app over the same lists, logic re-expressed in Power Fx.
Why
  • Fully native, governed, mobile, in the M365 admin estate.
Cost
  • Re-creating the calculator logic in Power Fx is real work.
  • Complex grid/matrix UIs are harder in canvas apps.
Part 3

Step by step to live.

Steps 1–4 get you shared & online on the Box + Vercel path — a coherent v1 in roughly 2–3 weeks of focused dev. Steps 5–7 only apply if you take the Microsoft / Fabric route for enterprise BI.

Pick your backend & set it up

You / IT half a day

Box (recommended): create a shared folder (e.g. PPM / Fee & Revenue System) and a Box app/API token so the web app can read & write a projects.json there. Set folder permissions for who can edit.

  • Airtable: create a base with the four tables from Part 1.
  • SharePoint: create the four Lists with the columns & Lookups from Part 1; turn on versioning.

Host the app on Vercel

You / Dev 1 hour

Push this folder of HTML files to Vercel (or any static host). You get a URL the team opens — it replaces “double-click the file.” Nothing about the app changes for this step; it's purely putting it online.

Point the storage layer at your backend

Dev 2–4 days

Replace the body of store.js — the only file that touches storage — so listProjects / getProject / saveProject / deleteProject read & write your backend instead of localStorage. Everything downstream (calculator, ingestion, projections, reconcile) keeps working because they only ever call those functions.

  • Box: pull projects.json on load, write it back on save, with a pull-merge-write + timestamp check so simultaneous edits warn instead of clobbering.
  • Airtable / SharePoint: map a record → rows across the tables on save; reassemble on load. Row-level writes, no clobber risk.
  • Auth via your provider's OAuth (Box / Microsoft) for governed, per-user access.

Load the Rates Catalog & migrate existing projects

You + Dev 1 day

Seed the rate grid (the PPM 2024 catalog), then use the app's Export DB → JSON to move everything built so far into the shared backend. For Box that's literally uploading the exported file as projects.json; for Airtable/SharePoint, a one-time import fans each record into the tables. From here the browser copy is retired.

Stand up the Fabric Lakehouse — SharePoint route only

Dev / Data 1–2 days

In Fabric, create a Lakehouse and a Dataflow Gen2 (or Data Pipeline) that pulls the four SharePoint lists on a schedule. This gives Power BI a clean, modeled source and keeps heavy queries off SharePoint.

  • Model relationships: Projects 1→N Roles, 1→N Phases.
  • Build the monthly billing series as a DAX measure (the same logic as our monthlySeries): rate × FTE × hours per phase-month, net of discount, by billing mode.

Rebuild the reports in Power BI — SharePoint route only

Data 3–5 days

Recreate what we prototyped as proper Power BI visuals — now refreshing live and shareable firm-wide:

  • Revenue Projections matrix — months across, projects down, sliced by the 1–7 rating, service line, client, leader, year/quarter/month.
  • Rating-weighted forecast — probability × billings as a measure.
  • Flash report & accruals — the monthly outputs, generated from the same model.

The rating weights, service-line tags, and billing modes we designed all become slicers and measures.

Wire the automations — any route

Dev ongoing
  • Clockify → Fabric: a scheduled pipeline pulls weekly time entries into the Lakehouse, joined to projects/roles by the mapping we built — that's planned-vs-actual P&L in Power BI.
  • Won → Salesforce: a Power Automate flow fires when a project's Status flips to Won, drafting the intake / schedule of values.
  • Aging: a scheduled flow flips Active projects to Closed once last-billing is >60 days past (the rule we already defined).
Part 4

What to know before you commit.

Box keeps it simplest. Because the whole database is one JSON file, the Box path is the closest thing to “what you have now, but shared.” The only engineering nuance is the save protocol (pull-merge-write) so two people saving at once don't overwrite each other — a small, well-understood pattern.
DAX caveat — SharePoint/Fabric route only. If you go the Power BI way, the rate math (today in JavaScript) must be re-expressed in DAX. Simplest fix: store the computed monthly billing series on save so Power BI just reads it. The Box/Airtable paths keep reporting in-app and avoid this entirely.
Start narrow. Box + Vercel + the reporting already in the app is a complete, shareable v1 — pilotable in ~2–3 weeks. Clockify and Salesforce automations layer on after, without rework.
