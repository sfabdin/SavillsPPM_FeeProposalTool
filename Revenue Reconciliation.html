Map every line to the fee tool Do this first — nothing else on the page is true until it is done

Every figure on this page is arithmetic on top of one assumption: that the line Finance billed and the project the fee tool prices are the same job. A line with no project has no EARNED figure to reconcile against, so it reads as revenue nobody forecast; a line pointed at the wrong project is worse, because it moves real money onto someone else's forecast and makes two projects wrong instead of one. There are only three answers: this project, a project we do not have yet, or not a project at all — and the third is a decision worth recording, not a gap. A mapping is kept in its own book, so it carries into every future close instead of being made again each January.

Upload Revenue by Month by Client and pick the YTD <Month> <Year> tab. One upload lands every month that tab carries — the July tab brings in January through July in a single go. Next month, upload the August tab and it refreshes in place, keeping every billing status you have already set. Columns are found by their header text, not their position, and every row is footed against the sheet's own Reported Revenue column before anything lands. Three lanes, one question per cell

Tool is what the fee record says should bill, straight from the project — read-only, because it is the plan being reconciled against. Billed is what the sheet says was invoiced; type over it when the sheet is wrong, and clear the cell to put the sheet's figure back. Accrued is earned but not invoiced, and you fill it in — the file cannot tell you. Recognised = billed + fee share + accrued.

Why the accrual has to be spread by hand

The close file states one accrual figure per project, with no month behind it. P009355 carries $680,000 against no billings at all — which is really $170,000 earned in each of April through July, and nothing in the file says so. No arithmetic can recover that, so the tool does not pretend to: the imported lump sits in the Accrual column as a target, the row shows how much is still unplaced, and Spread… fills an even run in one action. A row is right when the column reads allocated ✓.

One year at a time

The ledger starts in 2026 and only looks forward. The close file's prior-year accrual reversal is read at import — purely to prove the sheet parsed correctly against its own totals — and then discarded: it is a whole-year opening adjustment about last year's work. So this ledger's total deliberately differs from the file's "YTD Reported Revenue" by exactly that reversal. Prior years stay in Finance's own files.

Why fee shares sit below billed, not inside it

The invoice really did go out gross — the client was billed the full amount, and the co-broker's cut comes off Savills' revenue afterwards. Netting it into the billed figure would destroy the number Finance reconciles against, so every fee share stays its own line, indented under the project it comes out of. A fee share is signed: a reversal of a prior-period share shows as a positive month.

Where this is stored

Actuals live in their own Box file, revenue.json — never inside projects.json, which holds project records and nothing else. Re-posting a close would otherwise churn the file every other page reads. The file configures itself: the first admin to open this page creates it in the shared folder, and everyone lands on the same one. Edits merge per project row, so two people reconciling different projects at the same time both keep their work.

Who does what

  • Finance uploads the tab and rules on each figure. Only two things are pre-filled — fee shares, and billings that land on plan — and both can be changed.
  • Revenue leaders never touch this page. They see the result in Revenue Projections.
  • A slipped figure moves the money on the project. Pick the month it should bill instead and the fee comes off the month that missed and lands on the one you chose — the project's total is unchanged. The project is flagged, and both months show in red on Revenue Projections until someone marks the slip reconciled. It is the one thing on this page that edits a revenue leader's forecast, so it is deliberately loud. A line that isn't mapped to a project can't slip — there is no forecast to move.
